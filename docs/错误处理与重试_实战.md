# 🛟 错误处理与重试实战（生产化 3.3）

> 配套代码：`tests/demo_retry_errors.py`（6 patterns，`--all` 6/6 通过）
> 环境：strands-agents 1.53.x（venv: `uv sync` 重建版）
> 亮点：重试语义全部通过 monkeypatch `model.stream` **离线确定性仿真**，不烧 token

## 一、本版本 API 地图（与旧文档的差异！）

⚠️ 网上很多教程基于旧版本，以下是对照后的 1.53 实际状态：

| 概念 | 1.53 实际 | 说明 |
|---|---|---|
| 模型调用入口 | **`Model.stream(...) → AsyncIterable[StreamEvent]`** | 旧版的 `invoke()` 已不存在（全库 grep 无） |
| 默认重试 | `ModelRetryStrategy`（max_attempts=6, initial_delay=4, max_delay=240） | **只重试 `ModelThrottledException`** |
| 关闭重试 | `Agent(retry_strategy=None)` | 有哨兵对象 `_DEFAULT_RETRY_STRATEGY`，传 None 才是关闭 |
| 扩展重试 | 子类重写 **`is_retryable(exc)`** 一行 | backoff 状态机全继承 |
| 通用重试钩子 | `AfterModelCallEvent.retry = True` | 对**任意异常**生效；事件循环看到 retry 即 `continue` 重调 |
| 强制停止 | `ForceStopEvent`（`force_stop=True` + `force_stop_reason`） | 重试耗尽/不可重试时，在 raise 前 yield |
| 异常兜底 | `EventLoopException(original_exception=...)` | 部分路径保留原始异常于 `.original_exception` |
| 滑窗 | `SlidingWindowConversationManager(window_size=N)` | **按消息条数**裁剪（不是 token！），`pin_first` 固定头部 |
| 流式入口 | **`agent.stream_async(prompt)`**（异步生成器） | 不是 `stream()`/`stream_async` 命名混乱——以本版本为准 |

## 二、重试执行链（源码走读结论）

```
model.stream() 抛异常
   │
   ▼
event_loop except 分支
   ├─ 构造 AfterModelCallEvent(exception=e)
   ├─ hooks.invoke_callbacks_async(event)        ← 重试决策点
   │     ModelRetryStrategy._handle_after_model_call:
   │        is_retryable(e)? ─否→ return（放弃）
   │        attempt += 1; attempt >= max_attempts? ─是→ return
   │        await asyncio.sleep(delay)            ← 指数退避: 4→8→16→32→64(→240封顶)
   │        event.retry = True
   ├─ event.retry? ─是→ continue（丢弃响应重调模型）
   └─ 否则 yield ForceStopEvent(reason=e) 后 raise e
```

**两个容易踩的坑**：

1. **流式碎片事件已经发出去了。** 被丢弃的响应在重试前可能已向消费者 yield 过部分事件
   （官方 docstring 明文警告）→ 前端要能容忍/去重，别把半句话渲染进 UI。
2. **`event.retry = True` 就够，不需要清 `event.exception`。** 重试成功走新的事件对象，
   旧异常的残留不影响（我们最初以为要清，实测不需要）。

## 三、Patterns（demo_retry_errors.py）

| # | Pattern | 关键断言 |
|---|---|---|
| 1 | 默认 throttle 重试 | 2 次 `ModelThrottledException` + 1 成功 = **model 调 3 次**、结果正常 |
| 2 | 反例 + force_stop + 异常解包 | `ConnectionError` → model 只调 **1 次**、`ForceStopEvent(force_stop=true, reason=...)` 在 raise 前发出、异常原样穿透 |
| 3 | `ConnectRetryStrategy(ModelRetryStrategy)` | 重写 `is_retryable` 把 `ConnectionError` 纳入 → 3 次成功（本环境 WSL DNS 抖动就是这类） |
| 4 | `AfterModelCallEvent` hook 通用重试 | `retry_strategy=None` 也能对 `TimeoutError` 重试；一次失败即恢复 |
| 5 | 滑动窗口 | 3 轮对话后 `len(messages)` 稳定在 `window_size=4` 附近；manager state 暴露 `removed_message_count` |
| 6 | stop_reason + 异常家族 | `end_turn` 正常；7 个异常类各自的处置策略速查表 |

### 推荐的错误处理姿势（可直接抄）

```python
from strands import Agent
from strands.event_loop._retry import ModelRetryStrategy
import httpx


class NetworkResilientRetry(ModelRetryStrategy):
    def is_retryable(self, exception: Exception) -> bool:
        return super().is_retryable(exception) or isinstance(
            exception, (ConnectionError, httpx.TransportError, TimeoutError)
        )


agent = Agent(
    model=...,
    retry_strategy=NetworkResilientRetry(max_attempts=6, initial_delay=2, max_delay=60),
)
try:
    result = agent(prompt)
except ConnectionError as e:  # 重试耗尽后原样抛
    raise RuntimeError("LLM 端点持续不可达，检查 Ollama/proxy") from e
```

## 四、异常家族处置表

| 异常 | 何时 | 处置 |
|---|---|---|
| `ModelThrottledException` | 服务端 429/限流文案 | 默认自动重试（指数退避） |
| `ConnectionError` / httpx 网络错 | Ollama 宕机、proxy 抖动 | 纳入 `is_retryable`；耗尽后告警 |
| `ContextWindowOverflowException` | 上下文超窗且裁剪失败 | 换 `SummarizingConversationManager`；Ollama 的 "prompt is longer than the context length" 等文案 1.53 已映射到此 |
| `MaxTokensReachedException` | 输出被 max_tokens 截断 | `result.message` 已含部分文本；再调一次 agent 可续写 |
| `EventLoopException` | 事件循环兜底包装 | `.original_exception` 取原始异常 |
| `SessionException` / `MCPClientInitializationError` | 会话/MCP 初始化 | 启动期 fail-fast，别进重试 |

## 五、与 Ollama 组合的专属建议

- Ollama 无官方 429，`ModelThrottledException` 主要出现在 **proxy/Bedrock** 场景；本地最常见的错误是
  **连接类**（GPU OOM 断连、`/api/chat` 重置、WSL 跨网卡 DNS 抖动——本项目两次真实踩到）
  → 默认策略对它无效，**必须**用 Pattern 3/4 的路子扩展
- Ollama 超窗文案是英文自然语言（见 `OVERFLOW_MESSAGES` 集合），strands 已做映射；
  自定义模型时留意别用没有映射的文案，否则会以裸异常穿透
